# Database Standards — PostgreSQL 16 + pgvector

## Use SQLAlchemy 2.0 by Default

Models are defined once in `common/facetrack_common/models/`. Queries use the SQLAlchemy 2.0 style (`select()`), async sessions in the backend:

```python
stmt = select(Employee).where(Employee.status == EmployeeStatus.ACTIVE)
employees = (await db.scalars(stmt)).all()
```

Queries live in `backend/app/repositories/`, never in routers or Celery tasks.

Avoid raw SQL unless there is a clear technical requirement (e.g. a window function, partition maintenance, a pgvector operator the ORM doesn't express cleanly). When raw SQL is required:

- Use bound parameters (`text("... WHERE id = :id")`, `{"id": id}`) — never format user input into SQL strings.
- Document *why* raw SQL was necessary in a comment above the query.

## Database Design

- Every table has `id`, `created_at`, `updated_at` (timestamps as `timestamptz`, stored in UTC).
- Use foreign keys for relationships and unique constraints instead of "check before insert" logic (`employees.employee_code`, `attendance_days (employee_id, work_date)`, `recognition_events.event_uuid`).
- Use proper types: `date` for `work_date`, `timestamptz` for instants, `numeric` for scores only if needed, Postgres `ENUM` or check constraints for statuses/roles.
- `JSONB` only for genuinely variable data (ROI polygons, operating hours, settings values) — never as a shortcut around modelling.
- **Soft delete** for business tables (`deleted_at`). **Hard delete** for biometric data (`face_enrollments`, snapshots, unknown faces) — see `standards/18-privacy-and-biometric-data.md`.
- `recognition_events` is range-partitioned by month (`captured_at`); new partitions are created ahead of time by a scheduled job.

## pgvector

- Embedding columns use `vector(512)` (ArcFace) or `vector(128)` (SFace) and store `model_name` alongside — never compare embeddings produced by different models.
- The HNSW index on `face_enrollments.embedding` is for back-office similarity search (duplicate detection, unknown-face grouping). **Live matching uses the engine's in-memory FAISS index**, not database queries.
- Embeddings are encrypted at rest per requirements NFR-8; follow the project's encryption helper, do not invent a new scheme.

## Query Optimization

Avoid N+1 queries:

```python
# Bad — one query per row to load the employee
for day in days:
    print(day.employee.full_name)

# Good — eager load
stmt = select(AttendanceDay).options(selectinload(AttendanceDay.employee)).where(...)
```

- `joinedload()` — many-to-one / one-to-one (single JOIN).
- `selectinload()` — one-to-many / collections (second query with `IN`).
- `load_only()` or selecting specific columns — for large result sets and reports.
- Required indexes (minimum): `recognition_events (employee_id, captured_at)`, `recognition_events (camera_id, captured_at)`, `attendance_days (work_date, status)`; add indexes for every new filter/sort column used by a list endpoint.

Do not optimize blindly — check the query plan (`EXPLAIN ANALYZE`) for anything on `recognition_events` or `attendance_days`, which grow fastest.

## Migrations (Alembic)

Whenever models change:

```bash
alembic revision --autogenerate -m "add operating_hours to cameras"
alembic upgrade head
```

- Always review the autogenerated script before running it — autogenerate misses enum changes, server defaults and some index changes.
- Every migration has a working `downgrade()`.
- Never manually edit or delete applied migrations in a database with real data.
- Before destructive changes (dropping/renaming a column, changing a type):
  1. Identify what data is affected.
  2. Confirm the intended behaviour with the requester.
  3. Write a data migration if values need to move/transform.
  4. Consider backup/rollback before running it against real data.
- Migrations must be safe to run while the system is live (add nullable column → backfill → add constraint), since attendance is recorded continuously.

## Transactions

Use one transaction per business operation, opened in the domain service:

```python
async with db.begin():
    day = await attendance_repo.get_for_update(db, employee_id, work_date)
    apply_rules(day, event)
    await audit_service.record(db, actor, "attendance.update", day)
```

Use transactions (and `SELECT ... FOR UPDATE` where concurrent writers are possible) for:

- Recording a check-in/check-out from an event
- Applying a correction
- Day close (per employee-day)
- Enrollment and biometric erasure
- Any multi-table update
