# Documentation & Code Comments

## Code Comments

Write comments explaining **why**, not the obvious **what**.

```python
# Bad
votes += 1  # increment votes

# Good
votes += 1  # count only crops above the quality gate, so blurred frames can't confirm an identity (NFR-2)
```

Reference the requirement ID when code implements a specific rule (`# FR-23: day close marks Missing Check-out`). Do not fill code with comments that restate what the code already says.

## Project Documentation

`README.md` (root) and each package's README should contain:

- Project overview and component diagram
- Requirements (Python, Node, Docker versions)
- Installation and `make dev`
- Environment variables (pointing to `.env.example`)
- Database setup and migrations
- Engine setup: downloading/converting models, running against a sample video, adding an engine node
- Backend and frontend setup
- Running tests, lint and type checks
- Deployment (`infra/`)
- API documentation link
- Troubleshooting (camera won't connect, engine stuck in degraded mode, etc.)

Architecture decisions that change the stack or a core rule are recorded as an ADR in `docs/adr/`.

## API Documentation

The OpenAPI spec is generated by FastAPI from the routers and schemas — keep it accurate by always declaring `response_model`, `status_code`, `summary` and error responses on routers. Do not hand-maintain separate API docs that drift from the code.

For important endpoints (integration, enrollment, biometric erasure), add a description covering authentication, request body, response shape, possible errors and an example.
